# 交付与复核
## 分析模式
交付文件清单、业务分类、模板、规则候选与依据、数据缺口、异常及适用范围。
只看到对账单时，区分“公式已读取”“金额已复算”“来源已核验”；不能把公式存在当作金额通过。

## 复算模式
- 确认规则和生效期覆盖全部期间；精度、退款方向、含税/净额均明确。
- 对照原表实际值逐项检查，差异记录原值/复算值/原因；允许容差必须来自确认的精度政策。
- 所有文件/订单/回款重复项和修订版本均处理；异常不归零。
- 初始预付/亏损余额需有来源；闭环核对上期、本期及下期。
- JSON结果只证明结构化规则被执行，不证明合同、数据或模板真实正确。

## 生成模式
还需已确认模板、双方资料及出单版本；用户已明确授权无需重复请求。
不得擅自改变模板或收款资料，不覆盖原件。公式和值保留正确类型，账号保留文本。
生成后重新读取：账期、主体、币种、分成率、调整项、应付、公式错误与外部引用；对照复算结果。布局检查使用可用渲染工具；未能检查应说明。
只有完成生成和复核才称“已生成”；试算、草稿、正式单状态分开。
暂不结算的项目列原因、余额及后续条件。无需为一个异常整批停止。

## 分享与发布
通用方法/脚本/虚构样例可分享；真实账单、内部路径、合同参数、公司/账户信息留在仓库外。不要仅依靠.gitignore；检查暂存文件与差异。
保留用户指定仓库的既有访问范围，不能自行公开私有仓库。
引用开源格式不代表其他模型客户端都已实测。

## 验收层级
1. Skill格式和引用检查。
2. 固定计算单元测试与虚构样例。
3. 独立模型代理场景测试，记录实际行为；基线已通过则如实记录，不能编造改进。
4. 已确认历史业务金额回放及生成模板验证。
5. 不同厂商模型/客户端实测。
逐层报告，前三层通过不能写“确保零错误”或“已验证所有模型”。
